> 伊娃桌面宠物 · Android 单端
> v1.0 · 2026-10-09 · 面向 Android 研发 + 测试，拿到即可开工
> 周期：**5 个工作日** ｜ 产出：**一份填好的数据记录表 + 一个 Go/No-Go 结论**

## 0. 这份方案解决什么问题

M1 不做产品，只回答四个问题：

| # | 问题 | 为什么必须现在回答 |
|---|---|---|
| **H1** | 待机 CPU 能不能压到 1% 以下？ | **方案生死线**。压不到，序列帧路线不成立，整个技术方案要重评 |
| **H2** | 耗电是否真的无感？ | 决定用户会不会在第一天卸载 |
| **H3** | 国产 ROM 上能不能 24h 活着？ | 决定这个产品是「能用」还是「经常消失」 |
| **H4** | VP9 with Alpha 在目标机型能不能硬解？ | 决定 §3.2 的编码选型是否成立 |

**M1 的成功标准不是"功能跑通"，而是"数据达标"。** 功能跑通是 Day 1 的事。

## 1. Go / No-Go 判定门槛

> 先定门槛，再开始测。避免测完再找理由。

| 编号 | 验证项 | **Go 门槛** | 不达标怎么办 |
|---|---|---|---|
| **H1** | 待机 CPU（12fps，亮屏静止） | 连续 10min 均值 **< 1.0%** | 🔴 **No-Go**：降帧到 8fps 重测；仍不达标则方案重评 |
| **H2a** | 息屏 8h 耗电 | **< 0.5%** | 🟡 检查息屏是否真的停了渲染（预期应接近 0） |
| **H2b** | 亮屏 1h 相对无宠物基线的**增量** | **< 2%** | 🟡 降帧 / 换编码 / 减少画面更新区域 |
| **H3** | TOP5 国产 ROM 24h 存活率 | **≥ 90%**（白名单开启后） | 🟡 加大保活投入，或评估是否值得做 |
| **H4** | VP9 alpha 硬解命中 | **100%**（目标机型） | 🟡 换 HEVC with Alpha；再不行回退动画 WebP |
| **V1** | overlay 屏蔽范围 | 不设门槛，**摸底即可** | — 结果用于产品文案与降级策略 |
| **V2** | 内存增量 | **< 60 MB** | 🟡 降低解码缓冲帧数 |

**判定规则**：
- H1、H3 任一 No-Go → 召开方案评审会
- H2、H4 不达标 → 可在 M2 继续调优，不阻塞推进

### 2.3 测试素材准备

用一个**简化版伊娃**（不必等最终美术）生成 204 帧 PNG 序列，再编码成带 Alpha 的 VP9：

```bash
# 1) 生成 VP9 with Alpha（关键：yuva420p + alpha_mode=1）
ffmpeg -framerate 12 -i frame_%04d.png \
  -c:v libvpx-vp9 -pix_fmt yuva420p \
  -auto-alt-ref 0 -b:v 0 -crf 30 \
  -metadata:s:v:0 alpha_mode=1 \
  idle_vp9_alpha.webm

# 2) 同内容生成 HEVC with Alpha（备选方案对照）
ffmpeg -framerate 12 -i frame_%04d.png \
  -c:v libx265 -pix_fmt yuva420p -tag:v hvc1 \
  -crf 28 idle_hevc_alpha.mov

# 3) 生成一张静态 PNG 作为功耗基线对照
cp frame_0001.png baseline_static.png
```

**两个坑**：
- `-auto-alt-ref 0` **必须加**，否则 VP9 的 alt-ref 帧会让 alpha 通道出错
- `-pix_fmt yuva420p` 不能写成 `rgba`，Android 只认 yuva420p

## 3. 实验设计

### 实验 A · 播放链路可行性（Day 1 下午）

**目的**：确认 VP9 alpha 能在目标机型上硬解，且透明通道正确。

**步骤**：

1. 搭一个最小工程（见 §4），只有 `OverlayService` + `PetView`
2. 把 `idle_vp9_alpha.webm` 放进 `assets/`
3. 用 `MediaCodec` 解码到 `SurfaceView`，播放到悬浮窗
4. 逐机型跑 `H4` 检测

**硬解命中检测代码**：

```kotlin
fun probeDecoder(mime: String, w: Int, h: Int): String {
    val fmt = MediaFormat.createVideoFormat(mime, w, h)
    val list = MediaCodecList(MediaCodecList.REGULAR_CODECS)
    val name = list.findDecoderForFormat(fmt) ?: return "NONE"
    val info = MediaCodecList(MediaCodecList.ALL_CODECS)
        .codecInfos.firstOrNull { it.name == name }
    val hw = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
        info?.isHardwareAccelerated == true
    } else name.startsWith("OMX.") || name.startsWith("c2.")
    return "$name | hardware=$hw"
}
// 调用
probeDecoder("video/x-vnd.on2.vp9", 480, 480)
probeDecoder("video/hevc", 480, 480)
```

**判定**：目标 8 台机型全部 `hardware=true` → H4 通过。任一为 `false`，记录并在 §5 表格标注，决定是否切换编码。

**同时验证**：肉眼确认透明通道正常——背景全透、无黑边、无白边。若出现黑底，说明 alpha 没解出来，检查 `alpha_mode=1`。

### 实验 B · 待机功耗基线（Day 2 ~ Day 3 上午）★ 核心

**目的**：拿到 H1 数据。这是整个 M1 最重要的一组数。

**三组对照**（同机型、同素材、同场景，只改帧率/形式）：

| 组 | 形式 | 帧率 | 预期 CPU |
|---|---|---|---|
| B1 | 静态 PNG（不播放） | 0 | ≈ 0%（基线，用于算增量） |
| B2 | VP9 alpha 硬解 | **12 fps** | **目标 < 1.0%** |
| B3 | VP9 alpha 硬解 | **30 fps** | 观察上限成本 |

**测量步骤（每组重复 3 次）**：

1. 手机充满电，**飞行模式**，亮度固定 30%，关闭自动亮度
2. 清空后台，只启动伊娃悬浮窗
3. 静置 2 分钟让状态稳定
4. 采样 **10 分钟**：

```bash
PKG=com.eve.pet
PID=$(adb shell pidof $PKG)

# 方式一：top 连续采样（每 2s 一次，共 300 次 ≈ 10min）
adb shell "top -b -n 300 -d 2 -p $PID" > cpu_b2.txt

# 方式二：dumpsys 快照对比（推荐，更准）
adb shell dumpsys cpuinfo | grep $PKG     # 开始前
# …等待 10 分钟…
adb shell dumpsys cpuinfo | grep $PKG     # 结束后

# 内存
adb shell dumpsys meminfo $PKG | grep -E "TOTAL|Native Heap|Graphics"
```

5. **同时用 Android Studio Profiler 录一段 CPU 曲线**，作为交叉验证（命令行与 Profiler 数据若差异 > 30%，以 Profiler 为准）

**记录**：把三组的 CPU 均值、峰值、内存填入 §5 表格。

**判定**：
- B2 CPU 均值 < 1.0% → **H1 Go**
- B2 在 1.0% ~ 1.5% → 降到 8fps 重测
- B2 > 1.5% → **H1 No-Go，触发方案评审**

### 实验 C · 耗电验证（Day 3 下午 ~ 过夜）

**目的**：拿到 H2a / H2b。

#### C1 · 息屏 8h（过夜跑）

```bash
adb shell dumpsys batterystats --reset      # 重置统计
# 此刻记下电量百分比，锁屏静置 8 小时
adb shell dumpsys batterystats com.eve.pet | head -60
adb shell pidof com.eve.pet                 # 确认进程仍存活
```

**判定**：耗电 < 0.5% → H2a 通过。
若耗电明显偏高，说明**息屏没有真正停止渲染**，这是必须修的 bug（`ACTION_SCREEN_OFF` 未接管）。

#### C2 · 亮屏 1h 增量（对照组设计）

这是关键的控制变量法——**单独测"有宠物"没有意义，屏幕本身就是耗电大户**。

| 组 | 条件 | 记录 |
|---|---|---|
| C2-a | 亮屏 1h，**无**宠物（对照） | 耗电 X% |
| C2-b | 亮屏 1h，**有**宠物（12fps 悬浮） | 耗电 Y% |
| — | **增量 = Y − X** | **目标 < 2%** |

两次测试必须：同电量起点（都充满）、同亮度、同网络状态、同停留界面（建议停在静态桌面，不要滑动）。

**判定**：增量 < 2% → H2b 通过。

### 实验 D · 保活矩阵（Day 4 起跑，Day 5 收尾）

**目的**：拿到 H3。

**分两组对比**，证明"引导白名单"这一步是否真的必要：

| 组 | 条件 | 机型 |
|---|---|---|
| D1 | **不**做任何白名单引导，仅前台服务 + 常驻通知 | 全部 8 台 |
| D2 | 引导用户开启：自启动 + 电池优化白名单 + 后台高耗电允许 | 全部 8 台 |

**执行步骤**：

1. 每台机器装 App，启动悬浮窗，确认宠物可见
2. 记下起始时间，锁屏静置
3. **每 30 分钟**检测一次存活（写个循环脚本）：

```bash
PKG=com.eve.pet
for i in $(seq 1 48); do
  TS=$(date "+%H:%M")
  if [ -n "$(adb -s $DEVICE shell pidof $PKG)" ]; then
    echo "$TS ALIVE" >> keepalive_$DEVICE.log
  else
    echo "$TS DEAD"  >> keepalive_$DEVICE.log
  fi
  sleep 1800
done
```

4. 每台至少跑 **3 轮**（不同时间段），取平均

**记录**：填入 §5 保活矩阵表。

**判定**：
- D2 组 24h 存活率 ≥ 90% → **H3 Go**
- D1 组若显著低于 D2 → **证明白名单引导是必需的产品环节**（这是要写进产品方案的结论）
- 若 D2 仍 < 90% → 需要引入 `JobScheduler` 兜底重建，并在 M1 报告中标注

### 实验 E · overlay 屏蔽摸底（Day 4）

**目的**：V1，摸清"哪些 App 里宠物会消失"，用于产品文案。

**方法**：在装了悬浮窗的机器上，逐个打开以下 App，**截图对比**（宠物可见 = ✅）：

| 类别 | 待测 App |
|---|---|
| 支付 | 微信支付页、支付宝、云闪付 |
| 银行 | 招行、建行、工行、微众 |
| 安全 | 各大行安全键盘、政务类 App |
| 视频 | 抖音、B 站（全屏播放时是否被遮挡） |
| 游戏 | 任一全屏 3D 游戏 |
| 输入法 | 各主流输入法键盘弹出时 |

**批量截图脚本**：

```bash
adb shell screencap -p /sdcard/shot.png
adb pull /sdcard/shot.png ./shots/$(date +%s).png
```

**记录**：得到一份「屏蔽 App 清单」，直接交给产品写文案。

**延伸动作**：研究能否**程序化检测被屏蔽**——思路是给 `SurfaceView` 加一个 `Choreographer` 帧回调，
若连续 N 秒收不到 draw 但屏幕处于亮屏状态，判定为"被屏蔽"，**自动暂停解码省电**。
这个 hook 也建议在 M1 一起验证。

### 4.1 权限检查（含国产 ROM 二次校验）

```kotlin
object OverlayPermission {
    fun check(ctx: Context): Boolean {
        // 第一道：系统 API
        if (!Settings.canDrawOverlays(ctx)) return false
        // 第二道：AppOps —— 国产 ROM 上 canDrawOverlays 可能误报已授权
        val appOps = ctx.getSystemService(Context.APP_OPS_SERVICE) as AppOpsManager
        val op = AppOpsManager.OPSTR_SYSTEM_ALERT_WINDOW
        val mode = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
            appOps.unsafeCheckOpNoThrow(op, Process.myUid(), ctx.packageName)
        } else {
            @Suppress("DEPRECATION")
            appOps.checkOpNoThrow(op, Process.myUid(), ctx.packageName)
        }
        return mode == AppOpsManager.MODE_ALLOWED
    }

    fun request(ctx: Context) {
        ctx.startActivity(Intent(
            Settings.ACTION_MANAGE_OVERLAY_PERMISSION,
            Uri.parse("package:${ctx.packageName}")
        ).apply { addFlags(Intent.FLAG_ACTIVITY_NEW_TASK) })
        // 注意：Android 11+ 该设置页会忽略 package URI，直接落到总列表，属预期行为
    }
}
```

### 4.2 添加悬浮窗

```kotlin
val params = WindowManager.LayoutParams(
    WindowManager.LayoutParams.WRAP_CONTENT,
    WindowManager.LayoutParams.WRAP_CONTENT,
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.O)
        WindowManager.LayoutParams.TYPE_APPLICATION_OVERLAY
    else
        @Suppress("DEPRECATION") WindowManager.LayoutParams.TYPE_PHONE,
    WindowManager.LayoutParams.FLAG_NOT_FOCUSABLE       // 不抢焦点
        or WindowManager.LayoutParams.FLAG_NOT_TOUCH_MODAL // 宠物之外的触摸下传
        or WindowManager.LayoutParams.FLAG_LAYOUT_NO_LIMITS,
    PixelFormat.TRANSLUCENT
).apply {
    gravity = Gravity.TOP or Gravity.START
    x = 240; y = 900
}
windowManager.addView(petView, params)
```

> **点击穿透的实现**：View 尺寸**只包住宠物本体**，不要铺满全屏。
> 铺满全屏 + `FLAG_NOT_TOUCH_MODAL` 仍会吃掉自己的区域，导致宠物周围一圈点不动桌面。

### 4.3 MediaCodec 播放骨架

```kotlin
class PetView(ctx: Context) : SurfaceView(ctx), SurfaceHolder.Callback {
    private var codec: MediaCodec? = null

    override fun surfaceCreated(holder: SurfaceHolder) {
        val extractor = MediaExtractor().apply {
            setDataSource(context.assets.openFd("idle_vp9_alpha.webm"))
        }
        val trackIdx = (0 until extractor.trackCount)
            .first { extractor.getTrackFormat(it).getString(MediaFormat.KEY_MIME)!!.startsWith("video/") }
        val format = extractor.getTrackFormat(trackIdx)
        extractor.selectTrack(trackIdx)

        codec = MediaCodec.createDecoderByType(format.getString(MediaFormat.KEY_MIME)!!).apply {
            configure(format, holder.surface, null, 0)
            start()
        }
        // 循环喂帧（略）——注意 setOutputSurface 可用于无缝切换动作
    }
}
```

        (ctx.getSystemService(Context.POWER_SERVICE) as PowerManager)
            .let { pm ->
                // 用 BroadcastReceiver 监听 ACTION_SCREEN_OFF / ON
            }

        // 电量
        // ACTION_BATTERY_CHANGED → level < 20 && !charging → LOW_BATTERY
