# 伊娃桌面宠物 · 手机端技术方案

> v1.1 · 2026-10-09 · 用于立项评估
> **范围：仅 Android。** iOS 已移出本期范围（见 §1.2），相关分析保留在 §2 / §4.2 存档备查。
> 内容：渲染路线选型、保活策略、工作量与验收指标

---

## 0. 结论摘要

| 议题 | 结论 |
|---|---|
| **平台范围** | **仅 Android**。iOS 移出本期（系统不开放悬浮窗权限，做不出同等形态） |
| **渲染路线** | **序列帧**，不是实时 3D。编码用**带 Alpha 通道的视频**（VP9 / HEVC），硬件解码 |
| **包体增量** | **+6 ~ 9 MB**（对比实时 3D 方案的 +35 ~ 50 MB） |
| **待机功耗** | CPU **< 1%**，GPU 基本不动（对比实时 3D 常驻 5 ~ 15%） |
| **最大风险** | ① Android 12+ 起 App 可主动屏蔽第三方悬浮窗（银行/支付类）② 国产 ROM 后台保活 |
| **工作量** | 约 **19 ~ 31 人日**（Android 单端） |

**一句话**：Android 能做成真桌面宠物。渲染上别碰实时 3D —— 观感提升有限，代价是用户卸载。

## 1. 目标与非目标

### 1.1 目标
- 宠物常驻手机桌面，不打开 App 也能看见
- 长按唤起环形菜单，功能随手可达
- 待机时对续航与性能**几乎无感**
- 覆盖主流 Android 机型（含国产 ROM）

### 1.2 非目标（明确不做，避免范围蔓延）
- ❌ **iOS 端**（v1.1 起移出范围：iOS 无悬浮窗权限，「桌面常驻宠物」形态不成立，详见 §2）
- ❌ 实时 3D 可自由旋转视角（ROI 不成立，见 §3）
- ❌ 桌面图标替换 / 启动器插件（依赖 Launcher 生态，不可控）

## 2. 平台能力边界

> **v1.1 范围变更**：本节保留 iOS 对照，作为「为什么本期不做 iOS」的依据存档。
> 本期研发只需关注 Android 列。

**这是本方案最关键的一节。** 两端的差异不是"实现难度"，而是"系统给不给权限"。

| 能力 | Android | iOS 26 | 说明 |
|---|---|---|---|
| 桌面常驻悬浮 | ✅ `SYSTEM_ALERT_WINDOW` | ❌ | Android 用 `TYPE_APPLICATION_OVERLAY`（API 26+）可浮在**所有 App 之上**；iOS 无此权限 |
| 最佳可达形态 | 全局悬浮窗 | 主屏/负一屏小组件 | — |
| 自定义动画 | ✅ 悬浮窗内可画任意内容 | ❌ 小组件是"系统按时间线渲染的快照" | iOS 小组件**不支持任意 UI 动画**；GIF / MP4 / Lottie / 第三方渲染引擎会被 Jetsam 内存管理器直接杀掉 |
| 实时 3D | 技术上可行 | ❌ | 见 §3 |
| 点击交互 | 任意手势 | 仅能挂 Button/Toggle，且要么改数据、要么跳回 App | — |
| 灵动岛 | — | 可放小动画，**封顶 8 小时** | 苹果明文反对把 Live Activity 当常驻徽章用，滥用会烧掉活动配额 |
| 3D 壁纸 | 系统级 Live Wallpaper | ⚠️ Spatial Scenes 3D 视差 | iOS 的 Spatial Scenes 用的是**私有 API**，第三方不可用 |

### 2.1 三个必须提前知道的坑

**坑 1 · Android 12+ 可主动屏蔽悬浮窗**
系统提供 `HIDE_OVERLAY_WINDOWS`，App 可声明隐藏第三方悬浮窗。银行、支付、部分安全类 App 普遍启用。
→ 表现：**用户在这些 App 里看不到宠物**。这是系统行为，绕不过。
→ 应对：产品文案提前说明；检测到持续不可见时自动暂停渲染省电。

**坑 2 · 国产 ROM 后台保活**
vivo / OPPO / 小米 / 华为等定制系统后台管理极严，仅靠前台服务通知仍会在锁屏后被清掉。
→ 需 `AppOpsManager.checkOpNoThrow` 做权限**二次校验**（`canDrawOverlays()` 在某些机型会误报已授权）
→ 需引导用户开**自启动权限** + 加入**电池优化白名单**

**坑 3 · iOS 小组件的交互很弱**
用户点小组件只能触发一个 App Intent，然后要么改数据、要么跳回 App。
→ iOS 上「长按展开环形菜单」这套交互**无法复刻**，必须重新设计一套小组件语义。

## 3. 渲染方案选型

### 3.1 四条路线横向对比

| 方案 | 观感 | 包体增量 | 内存增量 | 待机功耗 | 开发量 | 结论 |
|---|---|---|---|---|---|---|
| **实时 3D（Unity）** | ★★★★★ | **+35 ~ 50 MB** | **+80 ~ 120 MB** | CPU 5~15%，GPU 持续唤醒 | 大 | ❌ 否决 |
| **实时 3D（Filament / 原生）** | ★★★★★ | +8 ~ 12 MB | +40 ~ 60 MB | CPU 3~8% | 大 | ❌ 否决 |
| **序列帧（精灵图 / 视频）** | ★★★★☆ | **+6 ~ 9 MB** | **+10 ~ 18 MB** | **CPU < 1%** | 中 | ✅ **采用** |
| **2D 精绘 + 伪 3D 动效** | ★★★☆☆ | +1 ~ 2 MB | +3 ~ 5 MB | CPU < 0.5% | 小 | ⚠️ 备选 |

**为什么否决实时 3D**：桌面宠物是 **7×24 常驻**场景，不是打开才跑的游戏。
实时 3D 意味着 GPU 持续唤醒，用户第一周就会因为耗电卸载。而它的收益只是"能转视角"——对宠物这个品类，**几乎没人在乎能不能转视角**。

> 佐证：市面上所有 Android 桌宠（Shimeji 桌宠、小鲸鱼挂件等）**没有一个**采用实时 3D 渲染，全部是"预设动画帧 + 优化的刷新机制"。
> Unity 做桌宠的实践也统一把 `Application.targetFrameRate` 锁到 **10 ~ 15**。

### 3.2 采用方案：序列帧 + 带 Alpha 视频编码

#### 3.2.1 编码格式选型

| 格式 | 体积 | 解码方式 | 功耗 | 兼容性 | 结论 |
|---|---|---|---|---|---|
| PNG 序列 / 精灵图 | 大 | CPU 软解 | 中 | 最好 | ⚠️ 备选 |
| 动画 WebP | 小 | CPU 软解 | 中 | Android 9+ / iOS 14+ | ⚠️ 备选 |
| **HEVC with Alpha** | **最小** | **硬件解码** | **最低** | Android 12+ / iOS 13+ | ✅ **首选** |
| **VP9 with Alpha** | 小 | **硬件解码** | **最低** | Android 10+ | ✅ Android 首选 |

**原因**：带 Alpha 的视频能用 **MediaCodec 硬件解码**，把解码负载从 CPU 挪走，这是序列帧方案能压到 CPU < 1% 的关键。
纯 PNG/WebP 序列帧走 CPU 软解，功耗反而下不来。

**推荐组合**：
- Android：**VP9 with Alpha**（覆盖 Android 10+，兼容性更好）
- iOS 备用：**HEVC with Alpha**
- 低端机 fallback：动画 WebP（降级但可用）

#### 3.2.2 资产预算

按伊娃形象 200dp 显示尺寸、@2.4x 渲染计算：

| 项目 | 数值 |
|---|---|
| 单帧尺寸 | 480 × 480 px |
| 动作数量 | 6 个（待机呼吸 / 眨眼 / 蓄力 / 飞一圈 / 打招呼 / 打盹） |
| 总帧数 | 约 **204 帧** |
| 单帧平均体积（VP9 alpha, 近似无损） | ≈ 30 KB |
| **视频资源合计** | **≈ 6.1 MB** |
| UI 资源（菜单图标、音效） | ≈ 1.5 MB |
| **总包体增量** | **≈ 7.6 MB** ✅ |

> 对比：Unity 方案光 runtime 就约 20 MB，加资源轻松破 35 MB。

#### 3.2.3 降帧策略（功耗控制的核心）

宠物绝大多数时间是**待机**，不需要高帧率。按状态动态调帧：

| 状态 | 帧率 | 触发 |
|---|---|---|
| 休眠（息屏 / 被遮挡） | **0 fps** | 完全停止解码与渲染 |
| 待机 | **10 ~ 12 fps** | 默认 |
| 交互（长按 / 动作播放） | **30 fps** | 用户触摸期间 |
| 降级（低电量 / 省电模式） | **5 fps** 或冻结 | 电量 < 20% |

**额外优化**：
- 待机动作做**无缝循环**，避免重复解码关键帧
- 检测到屏幕无变化（如处于全屏视频/游戏）时自动暂停
- 用 `SurfaceView` + `TextureView` 直接输出，跳过 View 层合成

#### 3.2.4 运行时内存

不预加载全部 204 帧。用 MediaCodec 硬件解码器流式解码，解码缓冲控制在 8 ~ 12 帧：

```
480 × 480 × 4 Byte × 12 帧 ≈ 11 MB
+ 解码器与 Surface 开销 ≈  5 MB
────────────────────────────────
内存增量 ≈ 16 MB
```

## 4. 技术架构

### 4.1 Android

```
┌─────────────────────────────────────────────┐
│  Foreground Service（前台服务 + 常驻通知）      │
│  └─ WindowManager.addView(TYPE_APPLICATION_OVERLAY)
│                                               │
│  ┌──────────────────────────────────────┐   │
│  │  PetView（悬浮窗根容器）                │   │
│  │   ├─ PetRenderer  ← SurfaceView        │   │
│  │   │    └─ MediaCodec (VP9 alpha)       │   │
│  │   ├─ RingMenuView（环形菜单，触摸时创建） │   │
│  │   └─ TouchHandler（长按 / 拖动 / 穿透）  │   │
│  └──────────────────────────────────────┘   │
│                                               │
│  StateMachine（休眠/待机/交互）→ 动态调帧率     │
└─────────────────────────────────────────────┘
```

| 模块 | 技术要点 |
|---|---|
| 悬浮窗 | `TYPE_APPLICATION_OVERLAY`；`FLAG_NOT_FOCUSABLE` + `FLAG_NOT_TOUCH_MODAL` 保证不抢焦点、不阻断下层触摸 |
| 权限 | `Settings.canDrawOverlays()` 判断 + `ACTION_MANAGE_OVERLAY_PERMISSION` 跳转；**再用 `AppOpsManager.checkOpNoThrow` 二次校验**（国产 ROM 必需） |
| 保活 | 前台服务 + 常驻通知（Android 8+ 强制）；`STOP_FOREGROUND` 不实现；引导白名单 |
| 播放 | `MediaCodec` + `SurfaceView` 硬件解码；`setOutputSurface` 支持无缝切动作 |
| 交互 | 本体区域 `FLAG_NOT_TOUCH_MODAL` 允许触摸；其余区域通过缩小 View 尺寸实现"点击穿透" |
| 状态机 | 监听 `ACTION_SCREEN_OFF/ON`、电量、前台应用，驱动降帧 |

### 4.2 iOS（已移出范围 · 存档）

> v1.1 起本期不做 iOS。本小节仅作为后续版本（若重启 iOS）的能力备查。

**明确：不做悬浮窗，做不到。**

| 能力 | 方案 | 限制 |
|---|---|---|
| 主屏形象 | WidgetKit 小组件 | 只能用 **2D** 静态图或纯 SwiftUI 矢量动画；不能是 3D 模型 / 视频 / Lottie |
| 常驻动效 | 纯 SwiftUI 矢量数学 + `drawingGroup()` | 可得连续动画，但仍是 2D；且低电量模式下系统会降级渲染 |
| 灵动岛 | Live Activity | **8 小时上限**，不适合常驻 |
| 3D 体验 | 只能进 App 内（SceneKit / RealityKit） | 离开 App 即消失 |

**产品建议**：iOS 端定位为「**小组件里的 2D 伊娃 + 点击进入 App 内的 3D**」，
不要对外宣传"桌面 3D 宠物"，避免预期落差。

## 5. 保活与功耗策略

### 5.1 保活（Android）

| 措施 | 必要性 | 说明 |
|---|---|---|
| 前台服务 + 常驻通知 | **必须** | Android 8+ 后台服务必须转前台；通知 priority 不能过低，否则会被系统清理 |
| 电池优化白名单 | **必须** | 引导用户 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` |
| 自启动权限 | **必须** | 国产 ROM 的关键；需按机型跳转不同设置页 |
| 权限二次校验 | **必须** | `AppOpsManager.checkOpNoThrow(OP_SYSTEM_ALERT_WINDOW)` |
| 进程被杀的恢复 | 建议 | 用 `JobScheduler` / `WorkManager` 兜底重建悬浮窗 |

**国产 ROM 适配清单**（需逐个跳转引导）：

| 厂商 | 设置路径 |
|---|---|
| 小米 / 红米 | 设置 → 应用设置 → 应用管理 → 权限管理 → 自启动 |
| 华为 / 荣耀 | 设置 → 应用 → 应用启动管理 → 手动管理 |
| OPPO / 一加 / realme | 设置 → 电池 → 应用耗电管理 → 允许后台运行 |
| vivo / iQOO | 设置 → 电池 → 后台高耗电 → 允许 |
| 三星 | 设置 → 电池 → 后台使用限制 → 从休眠应用中移除 |

### 5.2 功耗预算

| 场景 | CPU | GPU | 目标 |
|---|---|---|---|
| 息屏 / 被遮挡 | 0% | 0% | 完全停止 |
| 待机悬浮（10 fps 硬解） | **< 1%** | ≈ 0% | 连续 8h 耗电 < 3% |
| 交互中（30 fps） | 3 ~ 6% | 低 | 单次 < 30s |
| 长按菜单展开 | 5 ~ 8% | 低 | 单次 < 2s |

| R1 | Android 12+ App 主动屏蔽悬浮窗 | 银行/支付类 App 内宠物不可见 | **高** | 文案说明 + 自动暂停省电 + 引导进入 App 内查看 |

## 9. 附录：本方案用到的外部结论来源

- Android 悬浮窗：`SYSTEM_ALERT_WINDOW` + `TYPE_APPLICATION_OVERLAY`（API 26+），
  权限需 `Settings.canDrawOverlays()` + 设置页跳转，且 Android 11+ 设置页会忽略 package URI
- Android 12+ `HIDE_OVERLAY_WINDOWS`：App 可主动隐藏第三方悬浮窗
- iOS 26 WidgetKit：仍是「系统按时间线渲染的快照」，**不支持任意 UI 动画**；
  iOS 26 仅新增 Liquid Glass 材质与强调色渲染，架构未变
- iOS 灵动岛：Live Activity 单次最长 8 小时，苹果反对用于常驻状态展示
- iOS Spatial Scenes 3D 视差壁纸：**私有 API**，第三方不可用
- 桌宠行业实践：Shimeji 桌宠、小鲸鱼挂件等均采用「预设动画帧 + 优化刷新机制」

> 注：§3.2.2 的资产体积与 §5.2 的功耗为**基于同类产品的估算值**，
> 非实测数据，需在 M1 阶段用真机验证后再锁定。
