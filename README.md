## 产品演进 · 四个决策节点

这个项目换过三次形态、两次角色。演进链条如下，每一步的原因都记在这里，避免后人重复讨论：

| # | 决策 | 原因 | 结果 |
|---|---|---|---|
| **1** | 手搓瓦力机器人 → **手机 App** | 硬件核心件 ¥3600，成本劝退 | 转入软件形态，0 成本 |
| **2** | 瓦力 → **伊娃（EVE）** | 形象更适配「悬浮 + 发光即情绪」的交互语言 | 配色整体从暖锈转冷蓝 |
| **3** | 手机 App → **桌面宠物** | 常驻桌面比"打开 App"更符合陪伴场景 | 交互收敛为「长按 → 环形菜单」 |
| **4** | 双端 → **仅 Android** | iOS 无悬浮窗权限，「桌面常驻」形态不成立 | 范围收窄，工作量 −3~5 人日 |

> 节点 1~3 的产物都在 `legacy/` 与 `design/archive/` 里，**没有删除**。

## 关键结论速查

### 平台边界

| | Android | iOS |
|---|---|---|
| 桌面常驻悬浮 | ✅ `SYSTEM_ALERT_WINDOW` | ❌ 系统不开放 |
| 实时 3D | 可行但**否决** | ❌ |

**两个必须知道的坑**：
- Android 12+ 起 App 可**主动屏蔽**第三方悬浮窗 → 银行/支付类里宠物会消失（系统行为，绕不过）
- 国产 ROM 需 `AppOpsManager` 二次校验 + 自启动 + 电池白名单，否则锁屏几分钟即被杀

### 技术选型

| 项 | 选择 | 为什么 |
|---|---|---|
| 渲染 | **序列帧**，不是实时 3D | 常驻场景下 GPU 持续唤醒 = 用户第一周卸载 |
| 编码 | **VP9 / HEVC with Alpha** | 靠 **MediaCodec 硬件解码** 才能把待机 CPU 压到 1% 以下 |
| 菜单 | 环形 **R=132px**，贴边自动转 5 项扇区 | 屏宽仅 390px，桌面版 R=178 必溢出 |
| 面部 | **矢量实时绘制**，不是位图序列帧 | 「眼嘴联动」必须参数化，位图做不到；且素材体积从 MB 降到 0 |
| 面部与身体 | **两层解耦**，独立刷新 | 静态表情时面部层 0 帧；换表情不用重跑身体视频 |

### 核心指标

| 指标 | 目标 |
|---|---|
| 包体增量 | **+7.6 MB**（实时 3D 方案要 +35~50 MB） |
| 内存增量 | **+16 MB** |
| 待机 CPU | **< 1%**（实时 3D 是 5~15%） |
| 待机帧率 | 12 fps（息屏 0 fps） |
| 24h 保活率 | > 90% |
| 工作量 | **19 ~ 31 人日** |

## 技术备忘（踩过的坑）

- **ffmpeg 编 VP9 with Alpha**：必须加 `-auto-alt-ref 0`，否则 alt-ref 帧会让 alpha 通道出错；`-pix_fmt` 只能写 `yuva420p`，写 `rgba` 无效
- **抠像判据**：深底亮主体用 `img.min(axis=2)`（最暗通道）比洪水填充稳，再用 `binary_fill_holes` 保住黑色面板
- **环形菜单坐标**：必须用 `中心 + R·(cosθ, sinθ)` 统一算。凭感觉填会导致各项半径不等，菜单歪成不规则形状
- **环形菜单标签压字**：45° 间距弦长 `2R·sin(22.5°)`，R=118 时 90px 够用；扇区 30° 间距弦长 `2R·sin(15°)`，R=130 时仅 67px **会压字**，需 R≥145
